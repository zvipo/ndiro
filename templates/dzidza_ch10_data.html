This is the chapter closest to your home turf, so it moves fast and focuses on the web-specific parts: how a web app shapes its storage around access patterns, and how HTTP caching turns a slow photo store into a fast one.

Four tables, no GSIs, scans on purpose

DynamoDB is a key-value/wide-column store: you get O(1) access by partition key, ordered range reads within a partition by sort key, and (almost) nothing else. So you design the keys from the queries — the same access-pattern-first thinking as any HBase/Bigtable schema:

TablePKSKDesigned for
usersuser_id (Google sub)—Point reads on every request (the auth guard)
mealsuser_idsk = date#meal_idAll range queries below
sharesshare_token—Point read per share-link visit
invitesinvite_token—Point read + conditional claim

The meals sort key is the whole data model in one string: 2026-09-03#183042-a1b2c3 — date, then a meal ID whose prefix is the client-supplied time of day. Lexicographic order of the SK is chronological order, so:

{{ code_file('db.py') }} 
begins_with(sk, '2026-09-')            # one month  = ONE Query
between(sk, '2026-08-28#', '2026-09-03#~')   # any day window = ONE Query

(The #~ trick: ~ sorts after the digits, so the range is inclusive of the end day's meals.) A side effect worth knowing because it shows up in the UI: the time is part of the key, so editing a meal's date or time would be a delete+create, not an update — which is why edit mode disables those two inputs.

Everything that isn't one of those patterns — admin user listing, share/invite listing, the monitor stats — is a scan, and the code refuses to pretend otherwise. At ≤100 users a scan is microscopic; CLAUDE.md explicitly warns contributors not to "fix" it with GSIs. Complexity is spent where the access pattern is hot, and nowhere else.

⚠️ The Decimal discipline

boto3 refuses floats (binary floats can't round-trip through DynamoDB's decimal wire type), and Flask's jsonify refuses Decimals. Hence the rule stamped through the codebase: Decimal(str(x)) going in, float() coming out. Any diff that stores a raw float or serializes a raw Decimal will throw at runtime — in review, check both edges of every new numeric field.

Photos: private bucket, proxied bytes

Photos live in S3 at users/{user_id}/meals/{date}/{meal_id}.jpg — keys built server-side only, never accepted from a client. The bucket is private, and the app deliberately does not hand out presigned S3 URLs. Instead the browser fetches /photo/<date>/<meal_id> and the app streams the bytes itself, because putting the app in the path buys three things: every photo read passes the same auth guards as everything else (session for owners, token scope for shares), a revoked share stops being served immediately — a presigned URL keeps working until it expires, wherever it was forwarded, while here only a recipient's already-cached bytes linger, bounded by the one-day max-age below — and there's one choke point to rate-limit and cache.

The cache hierarchy

Proxying means paying an S3 round trip per photo view — unless you cache. Ndiro stacks two layers, and the versioning idea that makes them safe is the transferable lesson:

browser cache (per user)             in-process LRU (shared)          S3
    │                                        │                         │
    │  <img src="/photo/…?v=9f8a…">         │                         │
    │  hit: 0 requests (immutable, 1y)       │                         │
    │  miss ─────────────────────────▶ byte-budgeted dict              │
    │                                  hit: no S3 call                 │
    │                                  miss ─────────────────────────▶ get_object
  • Versioned URLs. The photo URL carries ?v=sha1(updated_at). Replace the photo and the URL changes, so caches never need invalidating — stale entries are simply never asked for again. Owners get Cache-Control: private, max-age=1y, immutable.
  • ETag/304. When a browser revalidates anyway, it sends If-None-Match; matching means a bodyless 304 Not Modified — headers, no bytes.
  • The LRU (db.py's _PhotoCache) is a byte-budgeted in-process cache (default 64 MB) — valid only because there's exactly one worker process (the backend chapter's bet, called in).
  • Share links get max-age=1 day instead of a year — so a revoked recipient's browser cache ages out in bounded time. Cache policy as access policy.
🐘 From your world

Version-the-key-instead-of-invalidating is content addressing — the same move as immutable HDFS block IDs or a build system keyed by content hash. The two hard problems collapse into one: no cache invalidation, only naming. And the ETag/304 exchange is a checksum-based short-circuit read, straight out of any replication protocol.

Deletion, ordered like a systems engineer would

Account deletion has no transaction spanning S3 and four tables, so order substitutes for atomicity: photos → meals → shares → invites → the users row last. Every prefix of that sequence is retryable, and the user row acts as the commit record — while it exists, deletion can be re-run. The admin monitor even counts "orphans" (meal rows and photo objects whose user row is gone) as a detector for the sequence having stopped part-way: a reconciliation check, not a hope.
